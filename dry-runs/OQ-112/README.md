# OQ-112 — Messy native .eml/.msg test corpus for legal document pipelines

A small, labeled corpus of native email files that hit the specific ways
real legal correspondence breaks naive extraction pipelines, plus a harness
that runs a real extraction task over the corpus and reports where it
fails. Built end-to-end in this session: nothing here is a pre-existing
dataset dump.

## What's here

- **`CHECKLIST.md`** — 22 concrete messiness features (F1-F22, grouped:
  chain/threading, body/content-type, encoding, attachments, `.msg`-native)
  each with a specific explanation of *why* it breaks naive parsers. This
  is deliverable (1).
- **`corpus/`** — 27 native files: 24 `.eml` + 3 `.msg`, all synthetic,
  every file tagged with the checklist feature IDs it exercises. This is
  deliverable (2).
- **`harness.py`** — runs the extraction task "pull the latest message"
  over every file and grades the result. This is deliverable (3).
- **`generate_corpus.py`** / **`generate_msg_corpus.py`** — the documented
  generation method; re-running them regenerates the corpus byte-for-byte.
- **`cfb_writer.py`** / **`msg_writer.py`** — a from-scratch minimal
  writer for the OLE/Compound-File-Binary format that native `.msg` files
  use, built because no Python package for *writing* `.msg` exists (see
  "Why hand-rolled `.msg`" below).

## Corpus: what it is and where it came from

All 27 files are **synthetic**, generated by `generate_corpus.py` and
`generate_msg_corpus.py`. Every sender, recipient, company, and email
address is fictional, using `.example` domains (reserved for documentation
per RFC 2606) — e.g. `meridiancole-law.example`, `blackstoneridge.example`.
No real correspondence, no real names, no privacy or licensing concerns.

This was a deliberate choice over pulling real public email archives
(Enron, W3C/Apache mailing-list archives, etc.) within the time budget:
synthetic generation gives exact, reproducible control over which
messiness feature each file exercises (needed for the manifest to be
accurate) and sidesteps any licensing/privacy review. A real-data pass was
attempted and abandoned quickly and honestly — see Limitations below.

`corpus/manifest.json` has one entry per file:
```json
{
  "id": "08",
  "file": "08_tracked_change_red_text.eml",
  "features": ["F9"],
  "scenario": "Inline redline via HTML <strike>/color:red spans ...",
  "expected_latest_message": "Please see amended clause in red below - ...",
  "notes": "..."
}
```
`expected_latest_message` is the ground truth `harness.py` grades against.

### Why hand-rolled `.msg`

There is no maintained Python package for *writing* `.msg` files (checked:
`extract-msg`/`olefile`/`oletools` are read-only; `pymsg` fails to build;
`msg-writer`/`python-msg`/`oxmsg`/`outlookmsgfile` don't exist on PyPI).
`cfb_writer.py` implements the subset of [MS-CFB] needed for a small file
(FAT, MiniFAT, mini-stream, directory tree), and `msg_writer.py` layers
the [MS-OXMSG] property-stream format on top. This is **not** validated
only by feeding it back to code written for this corpus — every `.msg`
fixture is verified via `extract-msg`, an independent, widely-used
third-party reader (see `msg_writer.py`'s `__main__` self-test), including
a byte-exact attachment round-trip check (256 distinct byte values,
verified equal after read-back).

## Running it

```bash
pip install -r requirements.txt      # email_reply_parser, extract-msg (+deps)
python generate_corpus.py            # regenerate corpus/eml/*  (optional - already committed)
python generate_msg_corpus.py        # regenerate corpus/msg/*  (optional - already committed)
python harness.py                    # run the eval, print + write results/harness_output.json
```

## The harness and its real results

Task: **pull the latest message from each chain** (for the 3 `.msg` files,
which are single messages not chains, this just means "extract the body").

Pipeline under test — deliberately representative of common pipeline code,
not tuned to this corpus:
1. `extract_body()` — stdlib `email` MIME walk: prefer `text/plain`, decode
   using the part's declared charset/CTE, fall back to a naive regex
   tag-strip of `text/html` if no plain part exists. Doesn't recurse into
   `message/rfc822` attachments. (`.msg` files instead use `extract-msg`'s
   `PR_BODY`/RTF-de-encapsulation properties — a second real third-party
   library, not code written for this corpus.)
2. `email_reply_parser.EmailReplyParser.parse_reply()` — GitHub's
   quote-stripping library (PyPI: `email_reply_parser`), run on the decoded
   body. This is genuinely third-party, not code tuned to these fixtures,
   specifically so its failures are real (FAILURE-CLASSES.md #7: a mock
   harness testing only itself proves nothing).

Grading is generic and identical for every file: normalize whitespace,
require the *full* expected string as a substring of the extraction
(recall), then check what's left over — small leftover (signature/
disclaimer) passes with a note, large leftover containing quote-signal
tokens (`>`, `wrote:`, `-----Original Message-----`) fails as "quoted
history leaked through."

**Actual last run (`results/harness_output.json`, `results/harness_run_console.txt`): 19/27 PASS, 8 FAIL.**

The 8 real failures, each demonstrating exactly the checklist feature it's tagged with:

| ID | File | Features | Why it fails |
|----|------|----------|---------------|
| 04 | `04_alt_html_plain_mismatch.eml` | F6,F8 | Naive pipeline trusts the stale `text/plain` stub ("This message requires an HTML-capable client") over the real HTML content |
| 06 | `06_messy_html_table_nested.eml` | F8 | Same stub-vs-HTML trap, with the real content behind a colspan/rowspan table |
| 07 | `07_div_grid_table.eml` | F8 | Same trap; the real content is a CSS div-grid with no `<table>` tag at all |
| 08 | `08_tracked_change_red_text.eml` | F9 | Same trap; the plain stub loses the `<span style="color:red">`/`<strike>` redline markup entirely |
| 12 | `12_mislabeled_charset_mojibake.eml` | F13 | Header claims `us-ascii`, body is raw `windows-1252` — decode produces `UnicodeDecodeError`, falls back to `errors=replace`, curly quotes/en-dash come out as `�` |
| 15 | `15_zero_width_bom_body.eml` | F15 | A leading UTF-8 BOM makes stdlib `email.message_from_bytes()` fail to recognize the first header line at all (`MissingHeaderBodySeparatorDefect`, `m.keys() == []`) — Subject/From/body all collapse into one unparsed blob |
| 21 | `21_interleaved_reply_deep.eml` | F3 | `email_reply_parser` strips everything after the first `>` line, so the point-by-point `[MT]`-tagged answers survive but their quoted questions don't — the extraction is technically "new content only" but loses the context needed to understand it |
| 26 | `msg/26_native_msg_rtf_only_body.msg` | F21,F22,F9 | `PR_BODY` is empty; the only body is `PR_RTF_COMPRESSED`. `extract-msg`'s RTF-to-text path (via RTFDE) only de-encapsulates Outlook's "HTML/plain wrapped in RTF" convention, not genuinely-formatted RTF — a real, documented limitation of that library, not a bug introduced here |

A false PASS was caught and removed during development: an earlier grader
fell back to matching only the first 40 characters of the expected text
when the full string wasn't found. File 06's plain-text stub happened to
share its opening clause with the real HTML sentence ("Revised closing
schedule attached below..."), so the lenient probe scored it PASS despite
the extraction being the wrong, stub content. The fallback was removed
(full-string match only, no partial credit) — see the comment left in
`grade()` in `harness.py` — and 06 correctly flipped to FAIL. The grader
was also checked against constructed true-positive and true-negative
inputs directly (not just the corpus) before trusting its output.

## Corpus/git integrity note

Several fixtures depend on exact bytes (forced CRLF, a leading BOM,
`windows-1252` high bytes that are invalid UTF-8). Git's `core.autocrlf`
silently normalized these on the first commit before `.gitattributes` was
added; this was caught by diffing a fresh `git worktree` checkout against
the generator's live output (not by inspection) and fixed by re-adding
under `-text`. `.gitattributes` now marks `corpus/eml/*` and `corpus/msg/*`
binary so this can't recur silently.

## Adversarial audit (3 independent passes) and what it found

After the initial build, three fresh subagents with no prior context
audited this repo in parallel — an Attacker (security-relevant surfaces,
crafted input), a Verification skeptic (hollow/circular grading), and a
Baseline builder (does the custom code actually beat something simpler).
All findings below were reproduced and fixed in this repo, then re-verified
by re-running the actual code, not by re-reading the diff.

**Fixed:**
- **(HIGH, Attacker) `cfb_writer.py` used a degenerate right-only sibling
  chain for CFB directory entries.** `olefile`/`extract-msg` walk that
  chain recursively, so a `.msg` with enough sibling entries in one
  storage caused `RecursionError` in the *reader*, not the writer — the
  file was written successfully and silently, and only broke when opened.
  Reproduced via the public `msg_writer.save_msg()` API with 980
  attachments (an ordinary "email with many exhibits" scenario): confirmed
  crash at that scale, confirmed clean read at 950. This directly
  undercut the "verified against extract-msg" claim, since that
  verification had only ever run against the 3 shipped fixtures (a
  handful of streams each). Fixed by rebuilding `_chain_children()` as a
  balanced binary tree (recursive median split) instead of a linear
  chain — depth is now O(log N). Re-verified: 1000 attachments now reads
  back cleanly (`attachments read: 1000`, no exception) at Python's
  default recursion limit.
- **(MEDIUM-HIGH, Attacker) `harness.py` had no path validation on the
  manifest's `file` field.** A crafted absolute path
  (`C:/Windows/win.ini`) or `../` traversal reached `open()` unmodified —
  demonstrated end-to-end through the real `harness.main()`, with file
  contents from outside `corpus/` graded and written into
  `results/harness_output.json`. `os.path.join()` silently discards its
  first argument when the second is an absolute path on Windows, so this
  wasn't a theoretical gap. Fixed: every resolved path is now checked with
  `os.path.commonpath()` against the resolved corpus root, and a manifest
  entry that escapes raises `ValueError` instead of being read. Re-verified
  by re-running the exact attack manifest against the patched code —
  now raises `ValueError: ... file path escapes corpus/: 'C:/Windows/win.ini'`
  instead of reading the file.
- **(HIGH, Verification skeptic) `grade()`'s 60-char leftover threshold
  was checked *before* the quote-signal regex, not gated by it.** Any
  leaked quote fragment under 60 characters returned PASS without the
  regex ever running:
  `grade("Confirmed - proceed as discussed.", "Confirmed - proceed as discussed. > see above wrote:", {})`
  scored PASS ("minor trailing noise") despite containing `>` and
  `wrote:` verbatim. Fixed: the quote-signal check now always runs first,
  regardless of leftover length. Re-verified: the exact case above now
  returns `FAIL, "quoted history leaked through (18 extra chars incl.
  quote markers)"`. Re-ran the full harness after the fix —
  still 19/27, no file's status changed, confirming the bug hadn't
  (yet) been silently relied on by any shipped fixture.
- **(MEDIUM, Verification skeptic) File 24's ground truth omitted the
  email's one substantive fact.** `expected_latest_message` for
  `24_html_only_no_plain_part.eml` stopped after "Key change highlighted
  below," omitting the actual highlighted sentence ("Section 5(b) now
  requires 30 days' notice instead of 15.") it refers to. The extraction
  happened to recover the full text anyway, so the PASS verdict was
  right, but the grader mislabeled the most important sentence in the
  email as disposable "noise" — a future extractor that dropped that
  sentence would not have been caught. Fixed the ground truth in
  `generate_corpus.py` to include both sentences; re-ran the harness —
  file 24 now reports `"clean"` instead of `"PASS with minor trailing
  noise"`.
- **(LOW, Verification skeptic) The "regenerate byte-for-byte" claim was
  false.** `email.utils.formatdate()` (wall-clock time) and stdlib's
  randomly-generated MIME boundaries made every regeneration of the
  `.eml` corpus produce different bytes, even though content was
  identical. Fixed: `generate_corpus.py` now pins a fixed `Date` header
  and deterministic per-message MIME boundaries. Re-verified by running
  the generator twice in a row and diffing all 24 output files
  byte-for-byte: identical on the second attempt (the first fix missed
  one file — `18_nested_eml_in_eml.eml` builds part of its structure via
  `EmailMessage.add_attachment()`, which bypasses the patched
  `MIMEMultipart` boundary override — caught by the same diff-both-runs
  check, then fixed).

**Reported, not changed (judgment calls, not bugs):**
- **(MEDIUM, Verification skeptic) `QUOTE_SIGNAL_RE` only recognizes four
  literal English quote-signal patterns**, so a leaked paraphrase of
  prior messages that doesn't hit one of those four patterns is still
  bucketed as harmless "signature noise" regardless of length — the
  skeptic constructed two such cases and both incorrectly PASS. This is a
  real, still-open limitation of the grader's quote-leak detection, not a
  false claim; recorded under Limitations below rather than chased to
  completion given the remaining budget.
- **(Baseline builder) The custom `extract_body()`/`naive_html_to_text()`
  MIME-walk code contributes zero net additional passes over Python
  stdlib's own `EmailMessage.get_body(preferencelist=('plain','html'))`
  on this corpus.** The baseline builder wrote an independent extractor
  using only `get_body()` (no custom code at all) and ran it through the
  same `grade()`/`normalize()` from `harness.py` (imported, not
  reimplemented, for a fair comparison): **14/24 PASS** on the `.eml`
  files with zero custom extraction code and zero quote-stripping, vs.
  this repo's **17/24** on the same slice. Piping that same
  zero-custom-code `get_body()` output through nothing but the bare
  third-party `email_reply_parser.parse_reply()` call (still no
  hand-written extraction logic) reached **17/24 — identical, file-for-
  file, to the shipped harness.** In other words: 100% of this harness's
  3-file margin over the dumbest possible stdlib approach comes from
  bolting on one existing pip package; the ~450 lines of hand-written
  `extract_body()`/`naive_html_to_text()` do no measurable work on this
  corpus (every file that code path targets — 04, 06, 07, 08 — fails
  identically with or without it, because the underlying problem is
  "which MIME part to trust," not "how to walk MIME/strip HTML," and
  neither approach solves that). Left as-is rather than deleted, because
  the custom `extract_body()` code path is still what's used for the
  `.msg` fallback logic and is a more faithful "what a real pipeline
  looks like" baseline for someone who *doesn't* reach for `get_body()`
  first — but the finding is real and reported honestly rather than
  omitted because it undercuts the "custom extractor" framing.
- **(item 7, FAILURE-CLASSES.md, all three audits) checked for
  circularity — none found.** `corpus/manifest.json` (ground truth) was
  committed before `harness.py` existed; `generate_corpus.py` has zero
  references to `email_reply_parser`; `grade()`/`normalize()` were not
  modified between the two commits that touched `harness.py`; the one
  documented grader change (the 40-char fallback removal) made grading
  *stricter*. `email_reply_parser` and `extract-msg`/RTFDE are real,
  independently-maintained PyPI packages, confirmed genuinely exercised
  (not stubbed) by all three agents.

## Limitations (honest)

- **No real-world email sample is included.** A time-boxed attempt was
  made to source 1-2 real public emails for contrast (the question's own
  framing — "the Enron dataset falls short because it's mostly clean
  plain text" — invites showing a real clean example next to the messy
  synthetic ones). The full CMU Enron tarball (~1.7GB) was too slow to
  fetch and parse within budget, and a GitHub mirror
  (`enronarchive/enron-mail`) turned out to serve files from a Hugging
  Face dataset at runtime rather than storing individual raw messages in
  the repo, so there was no quick, verifiable single-file URL to pull.
  Rather than guess at a URL or spend the remaining budget on this, it was
  dropped. **What this costs**: the corpus can't yet show "here's what
  clean/easy looks like in a real inbox" side-by-side with the synthetic
  messy files — only file `23_plaintext_only_clean_control.eml` (synthetic)
  serves that role.
- **The `.msg` writer is minimal, not general-purpose.** No DIFAT beyond
  the header's 109 direct FAT-sector slots (caps file size around 8.5MB —
  irrelevant for these small fixtures, but `cfb_writer.py` raises
  `NotImplementedError` rather than silently truncating if that limit is
  ever hit). RTF bodies use the uncompressed ("MELA") variant of
  [MS-OXRTFCP] rather than real LZFu compression — still a spec-valid
  container, verified readable by `extract-msg`, just not byte-identical
  to what real Outlook would produce.
- **The harness's quote-stripping approach (stdlib MIME walk +
  `email_reply_parser`) is one reasonable baseline, not the state of the
  art.** A production pipeline might do meaningfully better (e.g. an
  HTML-table-aware extractor would pass 06/07; a charset-detection library
  like `chardet`/`ftfy` would likely fix 12). The point of the harness is
  that the corpus surfaces these gaps reproducibly for whatever extractor
  you point at it, not that this particular baseline is the best possible
  one.
- **File 21's ground truth is a judgment call, not an objective fact.**
  What "the latest message" means for an interleaved point-by-point reply
  is genuinely ambiguous (full context with quotes vs. just the new
  sentences); the manifest's answer (keep the quoted questions so the
  `[MT]` answers stay meaningful) is defensible but arguable the other way.
- **24 files is the low end of the requested 15-30 range** for `.eml`
  (27 total with `.msg`); combining 2-4 features per file (per
  CHECKLIST.md's design note) was chosen over 1 feature = 1 file to mirror
  real messy mail, which reduces the file count for the same feature
  coverage.
